### ② 基线机制设计审查

- **floor 语义成立**：`Summary:95/90/0`（高于基线）判 CLEAN 退出 0；`Summary:91/88/0`（等于基线）判 CLEAN。floor（≥）不误伤合法新增断言。
- **"脚本永不自适应" 机械成立**：`svacheck.py` 全文**无任何写盘调用**（`write_text`/`json.dump` 命中 0）；`evidence.py`/`regress.py` 的 write_text 只写各自证据/摘要文件，从不写 `sva_baseline.json`。基线只能人工编辑，脚本无静默改写路径——此条**可机械验证**。
- **"changelog 留痕" 不可机械验证**（如实记）：`docs.py`/`report.py`/`regress.py` 对 `sva_baseline.json` **无任何内容守卫、无 sha-pin、无 changelog 校验**（仅 `spec.md` 被 sha-pin）。改基线值而不写 changelog，自动化不拦——「维护纪律（硬规则）」实为文档纪律，靠 /closeout 的 git diff 人工复核兜底。见 §C-新绕过 A。
- **`--no-baseline` 逃生口不会被滥用为常规路径**：`--no-baseline` 只在 `svacheck.py` CLI `main()` 里；`regress.py:44` / `evidence.py:61` 均以默认哨兵调 `scan_text`（恒加载基线），**不暴露该开关**。回归/证据的当前 build 判定必过基线。CLI 的 `--no-baseline` 供人工回扫旧 build 历史 log 用，且 CLI 不产证据（证据网关是 evidence.py），无法借它登假 ✅。
- **基线文件缺失真 fail-closed（实测）**：字节备份 + sha256 后临时改名 `sva_baseline.json`：

```
$ mv sva_baseline.json sva_baseline.json.MISSING_TEST
$ python3 scripts/svacheck.py -q floor_exact.log
SVA 基线文件缺失: …/sva_baseline.json —— 拒绝在无基线下判定（fail-closed，BUG-017 R1）。  退出码=1
# scan_text（regress/evidence 走的路径）同样 SystemExit fail-closed

```

CLI 与 `scan_text` 双路 fail-closed，删基线不能成为绕过手段。还原后 sha256 与备份逐字一致。

本项目自己的证据里就有这种格式——BUG-014 登记的真实失败行（bugs.md）：

```
"../tb/sva/packet_proc_core_sva.sv", 45: …a_done_hold: started at 155000ps failed at 165000ps  Offending 'done_o'
```

`a_done_hold` 正是今日回归 log 里以 `…failed at 1055000ps not finished`（0 失败态）现身的那条断言，其"失败态"引擎行会尾随 `  Offending 'done_o'`。实测该形态对两条正则：


端到端：`带 Offending 尾巴失败行 + 无 Summary`（无 -assert verbose / 被裁剪）→ svacheck CLI 判 `CLEAN 退出码 0`；`带 Offending 尾巴失败行 + 手改 0-failures 的 Summary` → 亦 `CLEAN`。
